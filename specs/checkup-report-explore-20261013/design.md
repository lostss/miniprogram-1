# 保单整理报告（探索版 · MVP 内测）设计

> 状态：探索版设计 · 2026-10-13 · 分支 `explore/checkup-report`（基线 `73abc6e`）
> 上游：`specs/mvp-report-20260929/design.md`（已被本轮**收窄**：只做"整理"，不做检视）

## 0. 定位

**把散落的保单整理成一份能逐条核对的清单。** 读者是代理人与客户**同看**（代理人操作手机，当面或微信里一起过），目标是让客户产生「我的保单你看清了」的信任；客户可带走一份脱敏回看版。

**产品阶段（2026-10-13 用户决策）**：

| 阶段 | 产物 | 状态 |
|------|------|------|
| 阶段一 | **保单整理报告**（本 spec）——只做归集/汇总/标注 | 当前；「当前报告降级成保单整理报告」 |
| 阶段二 | **保障检视报告**——在同一份报告上增加段落（缺口/条款责任/时间轴/观察） | 未来扩展方向 |

由此得出两条架构约束（**不建抽象**）：
1. 输出保持「事实白名单 + 分节」形状（`header/summary/groups/unassigned/pending`），阶段二＝在同一份数据上**增加段落**，不需要插件/主题机制
2. 阶段一的 `organize.js` **不得**掺入缺口/建议逻辑（那是阶段二的段落，混进来会同时破坏红线 1 与可判定性）

**落地形态（2026-10-13 用户澄清后修正）**：**调整当前报告页本身**——`pages/report/index` 的正文主体改为保单整理视图；原 AI 分析报告**结构保留、默认收起**（一行可展，内容一字未删），阶段一验完再决定是否删除。

- 曾试过并**已作废**的做法：新增独立页 `pages/checkup` + 入口 + `utils/explore-flags.js` 开关 —— 那是"并存"而非"降级"，且会造出第二套渲染实现。相关文件已删。
- 组装位置：报告页 `_applyReportData`（**唯一 choke point**）内调用 `buildCheckupReport` → 下拉刷新 / 客户版预览 / 分享加载等所有刷新路径自动同源。

三条红线（沿用，且是本次探索要验证的核心）：

| # | 原则 |
|---|------|
| 1 | 只出结果，不出建议——缺口/优先级/配置方案一律不做 |
| 2 | 不加形容词——只写「有什么 + 值」，不写好/坏/不足 |
| 3 | 不确定就标出来，不猜——缺字段、低置信、被保人未匹配，显式列出 |

## 2. 明确不做（本轮）

- 缺口 / 优先级 / 建议 / 评语（含"事实级观察"——延后，见 §5）
- 条款责任对照（依赖 `products` 建档，且应用侧目前零引用该集合）
- 保障时间轴 / 甘特图、保费三切面与缴费月历
- 现价表 / 回本
- AI 进入报告正文（本轮报告为纯规则产物，可复现）
- 快照/版本落库（最贵的持久化决策，等假设验证过再设计）

### 3.1 流程调整：上传入口从首页移到客户页（2026-10-13 用户决策）

| | 调整前 | 调整后 |
|---|---|---|
| 首页 | `<ocr-flow>` 无 `familyId`/`skipMatch` → 上传时必须**家庭匹配**（弹"匹配到哪家/新建"，新建时 `family_name = 投保人姓名`，`components/ocr-flow/index.js:681`） | 入口＝**新建客户**（跳客户列表页 `?action=create` 复用唯一一份建档表单）；首页不再有上传入口 |
| 客户页/家庭页 | `<ocr-flow skipMatch familyId>` 已省匹配 | 不变（**上传唯一入口**） |
| 匹配逻辑 | 两处入口并存 → 两条建档口径（一条按人数造占位、一条自动取名+角色+出生日期） | 首页入口取消后匹配成为死路径 → **可整块删**（`_runRoleStage` 之后的成员更新/角色判断 `roleInfer` 与匹配无关，**复用不删**） |

**两步走**：① 先改入口（本轮，已完成）② 真机验一轮后再删匹配逻辑（`components/ocr-flow` 的 match 阶段 + `session.cacheMatch` + "新建家庭"分支 + 首页 `<ocr-flow>` 挂载与其 `onOcr*` 处理器）。
理由：匹配是"上传时才知道是哪家"的能力，入口未验过就删码可能被要求加回。

### 3.2 骨架成员命名是契约（2026-10-13 查实并修正）

建档按"人数"造的占位成员必须命名为 **「成员1」「成员2」…**（`_shared/member-skeleton.js` 的 `skeletonName(i)`），不能是空名：

- 后端 `member-matcher.matchPoliciesToMembers` 在 OCR 写保单时会**按顺序认领**骨架成员（`target.name = name`），认领判定是 `^成员\d+$`；空名认不出来 → 真人名走"新建成员"分支 → 家里出现「N 个空名 + M 个真人」的成员污染
- 前端展示（整理报告）判断"这行是占位还是真人"必须用同一契约的 `isSkeletonName()`，不自写正则
- 该规则已加入 `scripts/sync-shared.js` 的 `CONTRACT_FILES`（第 15 个），前后端同源

**行为影响面**：后端逻辑**零变化**（正则只是从 `member-matcher` 搬到契约文件），变化来自前端产出的数据形态 → 云函数无需部署，随小程序发版即可。

### 3.3 角色确认不被 skipMatch 跳过（2026-10-13 修）

`_stageCtx`（primaryHolder / bloodNames）原先**只在 `_runMatchStage` 内部**构建，而家庭页上传走 `skipMatch` 会跳过它 → `_runRoleStage` 的 roleList 恒为空 → **角色卡不弹**；而成员 `role` 的唯一写入方就是角色卡（后端 `matchPoliciesToMembers` 只写 `name`/`birth_date`）→ 成员角色永远为空，`readiness` 与缺口推算的 `isPillar = role==='本人'||'经济支柱'` 随之恒假。首页上传入口取消后 `_runMatchStage` 更无调用方，角色卡彻底不可达。

**修法**：把 ctx 构建抽为 `_buildStageCtx(allPolicies)`，`skipMatch` 分支也调用它 —— **匹配弹窗仍跳过，角色确认照常**。纯前端改动，无需部署。

## 4. 内测判据（探索的验收，不是功能的验收）

同一份报告，2~3 位代理人各自与真实客户同看一次，记录：

| 信号 | 期望 |
|------|------|
| 客户是否主动追问（张数/保额/到期对不上） | 出现 ≥1 次 → 说明"整理"看进去了 |
| 客户是否愿意带走回看版（分享点击） | 出现 → 信任信号 |
| 代理人是否愿意第二次用（下次约见） | 出现 → 工具有留存价值 |
| 是否出现"这是不是推销/建议"的抵触 | 出现 → 红线 1/2 被违反，需改措辞 |

**kill criteria**：客户对清单无反应、或代理人觉得比"直接念保单"更费口舌 → 停止加码，不进入条款对照与时间轴。
