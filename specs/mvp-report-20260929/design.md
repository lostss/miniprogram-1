# 保障检视报告设计（前置检查报告 · MVP）

> 状态：设计讨论稿 · 2026-09-29
> 范围：只覆盖「报告」这一产物。上游定位见 §0。
> 关联：`docs/data-model-v2.md`（已决口径）、`docs/prd.md`、`CONTEXT.md`

## 0. 定位与边界

### 0.1 一句话

代理人与客户沟通**之前**的一张「检查报告」：把散落的保单整理成可核对的客观事实，代理人拿它去谈。

### 0.2 检验科原则（三条红线）

| # | 原则 | 具体含义 |
|---|------|---------|
| 1 | 只出结果，不出建议 | 「缺口 / 优先级 / 配置方案」一律不做——那是医生的活 |
| 2 | 不加形容词 | 责任对照只写「有 / 无 + 值」，不写「好 / 坏 / 不足」 |
| 3 | 不确定就标出来，不猜 | 计划取不到、条款未收录、字段低置信，一律显式标注 |

### 0.3 读者与形态

- **只给代理人看**。不做客户版、不做分享链接、不做 PDF（延后）。
- **快照**：生成即冻结。数据变更只标「待刷新」，由代理人手动更新；保留最近 3 版。
- 手机长图为主，**信息密度优先于美观**。

### 0.4 数据来源

| 来源 | 内容 | 性质 |
|------|------|------|
| 保单数据（OCR + AI 提取） | 险种 / 保额 / 保费 / 期间 / 被保人 | 唯一事实来源 |
| 手动补充项 | 家庭成员（**含无保单者**）、代理人批注 | 补纯 OCR 的盲区 |
| 条款主数据 `products` | 保障责任、附加权益 | **后台录入**，应用侧只读 |

## 1. 信息架构

| # | 段落 | 内容 | 数据来源 |
|---|------|------|---------|
| ① | 一屏摘要 | 客户名 · 成员数 · 保单数 · 数据时间 · 待刷新标记 | families + policies |

## 2. 逐段设计

### ② 总览卡（口径见 §4）

```
总保额 2310 万        其中一年期短险 2010 万（每年需续保）
年缴保费 1.2 万        保障型 40%  ·  储蓄型 60%
覆盖险种  重疾 / 医疗 / 意外        （寿险 缺）
```

### ③ 成员表

| 姓名 | 角色 | 年龄 | 保单数 | 来源 |
|------|------|------|--------|------|
| 张某 | 本人 | 43 | 5 | 来自保单 |
| 李某 | 配偶 | 41 | 0 | **补充** |
| 张小某 | 子女 | 8 | 3 | 来自保单 |

**手动补充的成员必须出现在矩阵里**——「一张保单都没有的人」在纯 OCR 数据里根本不存在，而「配偶完全没保障」恰恰是最典型的家庭风险错配。

### ④ 保障矩阵

- 行 = **家庭成员**（含无保单者），不是被保人。投保人/受益人放保单明细小字。
- 格 = 保额 + 期间：`50万 / 至2050-06-01`
- 空格用**留白**，不用红叉（中立性）
- 颜色深浅表示保额档位
- 点格子 → 跳到对应保单卡

### ⑤ 保障时间轴（候选杀手锏）

横轴年份、纵轴「成员 × 险种」，色条 = 保障期间，**缺口 = 空白**。
承载观察 1/2/3/5（见 §5）——单看一张保单没问题，拼起来才看得出「2028 年起孩子没保障了」。

### ⑥ 异常标注（仅事实层）

- 某成员某险种**完全缺失**
- 载明期限已过但状态仍为有效
- 90 / 180 天内到期
- 仍在等待期内
- 被保人未匹配到成员
- 保额 / 保费为空
- 产品条款未收录

### ⑦ 产品责任与权益

每张保单一张卡：

```
保障责任（条款：康健华贵B款医疗保险 · 计划二）
  等待期          30 日（疾病；续保不受限）
  续保            审核续保（不保证续保）；最高续保 84 周岁
  免赔额          年度免赔额 = max(10000 - 其他途径已补偿, 0)
  报销比例        100%（以医保身份就医并结算）；未按医保结算 60%
  年限额          计划二年限额见附表
  医院范围        二级及以上非营利/社保定点医院
  特药            恶性肿瘤特殊门诊（放化疗/靶向/免疫等）
  特殊门诊        恶性肿瘤 / 肾透析 / 器官移植抗排异 + 住院前后门急诊

附加权益
  [绿通] [特药服务] [体检]        ← 仅列条款写明的，不用行业通用名单补全

条款来源  自动匹配（产品名精确）      未收录 → 一行浅色说明，不给入口
```

- 责任项**动态生成**，概念字典为单一事实源
- 共用项恒显；差异项按保单计划取值；**计划缺失时该项显「需确认计划」，不猜**
- **不做跨产品责任对比**（需概念严格对齐，一个产品多一字段就崩）→ 第二版

### ⑧ 保费

一张卡 + 三切面切换，不做四张独立图表：

```
年缴保费合计 1.2 万
[按险种] [按公司] [按成员]
  ● 储蓄型 60%   ● 保障型 40%
─────────────────────────
缴费月历（12 格，峰值高亮）
```

- **按险种先聚两类**：保障型（重疾/医疗/意外/寿险）、储蓄型（年金/养老/教育/投连/万能/其他），小项为副。
- **按公司必须先归一**（否则「中国人寿 / 国寿 / 中国人寿保险股份有限公司」算三家）。
- 主次：按险种 > 按公司 > 按成员。

### ⑩ 待核对

低置信字段清单，每项可跳转修正。
⚠️ **前置条件**：`field_confidence` 的键名与顶层字段名不一致（见 §3.4），不对齐则该区不可用。

### ⑪ 规则生成的事实观察（可选，替代 AI 点评）

3~5 条，机器生成、零成本、零幻觉。**禁用词：建议 / 应该 / 推荐 / 优先 / 不足。**

## 3. 数据契约

### 3.1 products（一个条款 = 一条文档）

```js
{
  product_name: '康健华贵B款医疗保险',
  aliases: [],                        // 名称写法差异走这里（如「康健华尊医疗保险(费率可调)」）
  insurer, category,                  // category 英文枚举，需与 policies 中文枚举映射
  liability: { waiting_period, renewal, reimbursement_ratio, ... },  // 所有计划一致
  plans: { '计划一': { annual_limit: '...' }, '计划二': { ... } },    // 仅差异项
  benefits: ['绿通', '特药服务'],       // 权益通常不分计划，放顶层
  status: 'confirmed'                 // 报告只消费 confirmed
}
```

**不变量（各配一条测试）**

1. 同一个概念键**不得**同时出现在 `liability` 与 `plans` 里；
2. 计划取不到时不猜——差异项显示「需确认计划」，共用项照常渲染。

### 3.2 匹配路径

```
product_name 精确命中
  → 未中 → aliases 精确命中
    → 未中 → 判为「条款未收录」（不做模糊归一）
```

**禁止剥离括号做归一**：实测会把「康健华贵B款医疗保险」错配到「(计划二)」（库内两者并存）。

计划名来源：保单 `insurance_type`（实测康健华贵B款存的是 `"计划二"`）。
该字段语义混装（有时是险种细分、有时是计划），**只有取值落在 `products.plans` 的键里才当计划**。

### 3.3 policies 需要的字段

- `plan`（或沿用 `insurance_type` 并做校验）
- `annual_premium` 恒为**年化**值（见 §4）

### 3.4 待核对键名对齐

实测：`field_confidence` 里是 `insurance_company`，顶层字段却叫 `insurer`；另有 `insured_birth_date` 等顶层不展示的字段。
**不解决则「保险公司」永远标不出待核对、「出生日期」标了却没处看。** 需一张映射表或统一命名。

### 3.5 来源标注体系（成员与条款共用）

| 标记 | 含义 |
|------|------|
| 不标 | 来自保单 / 自动精确匹配 |
| 补充 | 代理人手动录入，无保单记录 |
| 待核对 | 提取出来但未匹配上 |

## 4. 口径（所有消费方必须同源）

| 口径 | 定论 | 依据 |
|------|------|------|
| 金额单位 | DB 存**元**，展示 ≥1 万转「x.x 万」 | `amount.js` |
| 险种归一 | 中文（`重疾险/医疗险`）↔ 英文（`critical_illness/medical`）双向映射 | 实测两集合枚举不同名 |
| 短险单列 | 一年期保单的保额/保费单列，注明「每年需续保」 | `isOneYearPolicy`；实测本户 87% 为短险 |
| 保额口径 | 医疗险报销年限额**计入**总保额，不拆报销/给付 | `docs/data-model-v2.md` 已决 |
| 保费年化 | `annual_premium` 恒为年化值（月缴×12、季缴×4、半年×2、趸交单列） | 否则月缴保单少报约 12× |

## 5. 事实观察清单（不需要收入即可生成）

**时间维**：① 保障时间轴断档 ② 集中到期（保障悬崖）③ 缴费期 vs 保障期错配 ④ 等待期内 ⑤ 已过载明期限但仍有效
**结构维**：⑥ 覆盖倒挂（非支柱厚、支柱裸奔）⑦ 保障杠杆 = 保障型总保额 ÷ 年缴保费 ⑧ 保障型/储蓄型保费比 ⑨ 同一成员同一险种 ≥2 张 ⑩ 保额内部横向异常 ⑪ 受益人缺失/法定
**成本维**：⑫ 保费三切面 ⑬ 缴费月历峰值 ⑭ 公司集中度
**质量维**：低置信字段 · 被保人未匹配 · 状态异常 · 外币保单

## 6. 明确不做

- 额度测算、缺口金额、优先级推荐、配置方案（需收入/负债，属「诊断」）
- AI 叙述性点评（输入与读者所见同源，只能同义改写）
- 客户版 / 分享链接 / PDF
- 跨产品责任对比
- 应用内条款录入（后台完成）
- 现价表 / 回本年限

## 8. 验证记录（2026-09-29 线上实测）

环境 `cloud1-3gan2ae3d3b400f1`；规模 families 1 / members 3 / policies 13 / products 8。

| 验证项 | 结果 |
|--------|------|
| 产品集中度 | 13 张保单 / **13 个不同产品名 = 1.00**，零复用 |
| 名称匹配率 | 原始精确 46% → 去括号 54% → 双向包含 62%（**且当场错配一次**） |
| 错配案例 | `康健华贵B款医疗保险` → `(计划二)`：剥离括号后同名，先命中者胜 |
| 计划信息 | 已在数据里：保单 `insurance_type = "计划二"` |
| 康健华尊两张 | `special_agreement` 均指向「(费率可调)」版 → 同一份条款，应合并 aliases（**修正**早前「拆两条」的判断） |
| benefits | 8 条 products 的 `benefits` **全为 `[]`** → 权益列示目前零数据 |
| field_confidence | 键名为 `insurance_company`，与顶层 `insurer` 不一致 |

**结论**：走「product_name 精确 + `insurance_type` 取计划」这条路径，字符串归一的全部风险都不存在；待办集中在**后台建档**，不在应用逻辑。
