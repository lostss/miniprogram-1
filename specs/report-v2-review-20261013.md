## 三、必须改的四条（含改法）

### 1. L0/L1/L2 → 映射到已有 `readiness` 三态，不造第三套分级

| v2.0 说法 | 代码对应 | 判定依据 |
|---|---|---|
| L1 完整数据（收入+负债已知） | `readiness = ok` | 有成员 + 支柱有年龄 + 有保单 + 有收入 |
| L2 基础数据（仅保单） | `readiness = degraded` | 无家庭收入且无成员收入 → 放行、产出**定性**分析（已有页头常驻披露） |
| L0 角色判断（收入缺失） | `degraded` 的子情形 | 缺口可信度 `gapReliability=blocked`（寿险/意外缺收入） |
| 硬阻断 | `readiness = blocked` | 无成员 / 支柱缺年龄 / 无保单 → 422 不可生成 |

**要求**：文档与 UI 一律沿用 `ok / degraded / blocked` 与 `confirmed / estimated / blocked`，**禁止新增 L0-L2 术语**（三套分级并存必然漂移）。

### 2. 删掉 0-100 加权总分，全场景改用分档（红 / 黄 / 绿）+ 单项事实

三个独立理由：
- **不可解释**：40/30/20/10 无精算或行业来源，代理人被问"为什么 62 分"无法回答（且无 CI 可回归）。
- **越红线**：加权分数隐含"保障好/不好"的价值判断，撞自家三不原则第 1 条。
- **违背错误不对称**："负面结论必须有明确依据支撑"——分数给不出依据。

**改法**：只出分档结论 + 单项覆盖率/金额。若将来坚持要分数，前置条件三条（缺一不做）：仅 L1 完整数据算、公开权重与算法、文案标注"内部一致性指标，不构成评价"。

**命名冲突提示**：报告中出现的任何"分"必须区分"**资料完整度**"（`calcCompletenessScore`，数据齐不齐）与"保障充分性"，禁止都叫"评分"。

### 3. 甘特图分两步：先"保障节点条"，"空白期/重叠"等补字段后再做

- **可先做**：时间条渲染（数据齐：`effective_date`/`expiry_date`/`coverage_term`(105=终身)/`payment_period`/`premium_term`，`policy-status.js` 已有 `isLifetimeTerm/isSinglePayTerm/isOneYearPolicy`），直接复用 `timeline-builder.js` 的节点数组。
- **不能做**：**医疗险重叠判定无数据基础** —— `docs/data-model-v2.md:177-179` 明确决策"不按报销型/给付型拆分"，无字段就只能靠产品名/AI 猜 → 制造误报，违反错误不对称。
- **断档预警**对一年期医疗险是伪警报（续保 ≠ 到期）。
- **前置条件**：补 `reimbursement_type`（报销型/给付型）字段 + 一年期险的续保语义，再开重叠检测。
- **铁律**：**没有字段的判定不出**。

### 4. 条款溯源引用：先补数据与消费端，否则模块不可交付

- 现状入库 = 概念化字段 + PDF 外链，**无"责任免除第 X 条"级原文/条目号**；`reportAI` 完全不读 `products`。
- v2.0 自带的兜底"该产品条款暂未收录"**是这条设计里最成熟的句子**——但按 8 个产品的进度，绝大多数保单都会落到这句话，模块只剩成本。
- 先做两件独立的事：① 建档时保留**原文段落 + 条目号**（`extract-pdf.js` 已拿到全文，只是没入库）；② 消费端按产品名匹配并注入。
- **不要上向量检索**：8 个产品量级用关键词精确匹配 + 条款版本号更可靠、可缓存、可抽检。
- **免责前置的实现方式（本次已落地）**：页头一行轻提示（`pages/report/index.wxml` `.title-ai-note`）+ 页尾完整声明保留。动机：免责是"以条款为准"的可追溯锚点，只放末页等于"没翻到就没有"；页头一行不打断叙事（化验单的免责也在末页，但页头有医嘱提示）。

## 四、四条次级修正

| # | 项 | 修正 |
|---|---|---|
| 1 | 产品级缓存 | 同客户内产品重复率低，**跨客户复用**才有价值；缓存键必须含**条款版本**（否则条款更新后旧结论被复用 = 误报）。更简单的等价做法：**建档时预计算**（离线 + 人工抽检），报告期只做注入 + 翻译 → 成本本就不随保单数线性增长 |

| 4 | TOP-N 风险预警排序 | "按急重缓轻、不按险种"方向对，但**排序依据要可解释**：定为 `gapPriority`（high/medium/low，`gap-core.js:32`）+ 是否 `blocked` 可信度，**不引入主观序**。现状只有逐成员三态点（`report-builder.js:159 buildHero`），TOP-N 排序器属新建 |
