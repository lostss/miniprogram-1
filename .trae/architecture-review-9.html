同步逻辑集中，无循环

Problem

fact-write 与 member-write 互相 require。member-write 顶层 const factWrite = require('./fact-write') 走 namespace 访问；fact-write 在 addFact 内部 lazy require member-write。两套不同的绕行方案本身就是 friction 信号——sync 逻辑被劈成两半，locality 丢失。

Solution

抽出 fact-member-sync.js，持有 FACT_TO_MEMBER_FIELD 映射与两个同步函数。fact-write 与 member-write 各自单向 require 该 module，循环消失。

Wins
  • ▸ locality: fact↔member sync 集中到一处
  • ▸ 删除两套循环依赖绕行 hack
  • ▸ interface 可独立测试 sync 逻辑
  • ▸ 删除测试通过：复杂度集中而非消失
Deletion test: 删掉 sync module，逻辑会重新散回两个文件——它 earn its keep。

两个 adapter 证明 seam 真实

Problem

_dispatch 同时持有两条调用路径：成员/财务走 in-process memberRepo，保单/事实走 cloud.callFunction('dataWrite'/'dataQuery')。"写到哪"的决策散落在 switch case 里，测试时无法绕开 cloud.callFunction。

Solution

引入 dataGateway interface，两个 adapter：InProcessAdapter（memberRepo）与 CloudFunctionAdapter（_callWrite/_callQuery）。_dispatch 只对 gateway 说话。

Wins
  • ▸ leverage: 一个 interface，N 个 tool 调用点
  • ▸ tests: 注入 mock adapter，免 cloud.callFunction
  • ▸ locality: "写到哪"决策集中到 gateway
  • ▸ 两个 adapter 证明 seam 真实存在
ADR 注意: 第 8 轮注释明确 "成员/财务走 memberRepo（进程内）；保单/事实经 dataWrite 网关" 是有意为之（性能）。本候选不推翻该决策，只是把已有 seam 形式化。

每个 module 变深，死代码消失

Problem

calc-age.js（26 行单函数）与 completeness.js（16 行单函数）是 shallow module——interface 与 implementation 几乎等宽。dataWrite/_shared/format.js 是 零引用死代码，因 sync-shared 只 prune 权威源中存在的文件，而 format.js 不在权威源，得以残留。

Solution

① 删除 format.js（deletion test 通过：复杂度不重现）。② calc-age 并入 memberRepo 或新 member-utils（年龄计算仅服务于 member 上下文）。③ completeness 并入 familyView（它消费 family+members+policies，正是 familyView 的领域）。

Wins
  • ▸ locality: 年龄计算贴着 member 逻辑
  • ▸ 完整度算法贴着 family 视图组装
  • ▸ 删除 1 个死文件，减少认知碎片
  • ▸ _shared 目录变浅，导航成本下降
注意: report-fields.js（28 行）虽小但是 write/read 双向契约的单一事实源，不属浅模块——不可合并。

每章独立，orchestrator 变 thin

Problem

report-builder.js 单文件承载 buildChapters、buildGaps、assessDataCompleteness 及多个章节构建逻辑。改一个章节要在 583 行里定位，locality 差；章节构建逻辑无法独立测试。

Solution

按章节拆 chapters/ 目录（overview / panorama / plan / timeline / urgent），共享 helper（buildGaps、统计）入 shared/。report-builder.js 退化为 thin orchestrator。

Wins
  • ▸ locality: 每章逻辑贴在自己的文件
  • ▸ interface 可单章测试
  • ▸ orchestrator 变 thin，深度提升
Speculative 因为: 583 行不一定等于 shallow——若章节间共享 helper 密集，拆分后可能产生跨文件耦合。需先读全文确认章节边界是否干净。
Top recommendation

先做候选 1：打破 fact-write ↔ member-write 循环依赖

循环依赖是 4 个候选里 friction 最明确、方案最干净的。两套绕行 hack（namespace + lazy require）本身就是信号； 抽出 fact-member-sync.js 后，sync 逻辑获得 locality， 两个领域 module 各自单向依赖，测试面收敛到一个 interface。改动范围小（两个文件 + 一个新文件）， 风险低，收益直接。其余三个候选可在本轮之后按 Worth exploring → Speculative 顺序排期。
