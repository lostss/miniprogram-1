候选 #1 · safeUpdate / safeQuery 在 dataWrite 中被 13+ 处绕过 Strong

涉及文件
cloudfunctions/dataWrite/handlers.js · cloudfunctions/_shared/db-helpers.js
问题

db-helpers.js 导出 safeQuery / safeUpdate / safeUpdateMany， 承诺"统一注入 _openid 防越权"这一安全不变量。但 handlers.js 中 21 个 handler 大量裸调 db.collection().where().update() / db.collection().doc().update() 绕过它们。

绕过点（节选）：

L306:  db.collection('facts').where(...).update(...)                    // addFact supersede
L333:  db.collection('facts').doc(factId).update(...)                   // updateFactConfidence
L376:  db.collection('families').where(...).update(...)                 // updateFamilyHandler
L575:  db.collection('families').where(...).update(...)                 // setStage
L732:  db.collection('members').doc(...).remove()                       // deleteMember 硬删
L789:  db.collection('policies').doc(target._id).update(...)            // deletePolicy 软删
L870:  db.collection('policies').doc(target._id).update(...)            // updatePolicy
L893:  db.collection('facts').doc(...).update(...)                      // deleteFact
L950:  db.collection('policies').where(...).update(...)                 // writeCashValue 回写

更糟糕的是命名冲突的历史疤痕——updateFamilyHandler、deleteFamilyHandler 是为了避免与 db-helpers 导入的 updateFamily 冲突而重命名的。Handler 层与 db-helpers 层处于同一抽象层级，命名空间碰撞本身就是接缝不清的信号。

深化方向

把"对某集合的写入"作为唯一接缝，所有 handler 必须经过它。该接缝统一注入： _openid（安全）、updated_at（审计）、markFamilyMutated（脏标记）、_advanceStage（stage 推进）。 使绕过成为不可能，而非依靠开发者自律。

收益
  • Locality：安全不变量集中一处，新增 handler 自动获得保护
  • 测试性：可对写入接缝做单测（注入是否生效、stage 是否推进）
  • AI-navigability：理解"所有 families 写入都校验 _openid"无需通读 21 个 handler

候选 #2 · conversationAI 的 _handlePostProcess 是 216 行五模式巨函数 Strong

涉及文件
cloudfunctions/conversationAI/index.js (L472-688)
问题

文件头注释（L2-8）声称"三模式架构：getPrompt / generateText / postProcess"。但 _handlePostProcess 内部实际包含五种互异分支： 

L481-486  CONFIRM 拦截  : {CONFIRM:xxx} 正则 → _handleConfirm
L488-492  KEEP 拦截    : {KEEP:xxx} 正则 → _handleKeep
L494-507  sug 拦截     : 匹配上一条 suggestions 数组 → 转 CONFIRM/KEEP
L520-634  正常工具路径 : safeCallChatWithTools → _dispatch 12 case
L644-687  持久化 + 日志 : 写 user/assistant 消息 + agent_logs

同时 _dispatch（L51-106）是 12-case switch，其中 deleteMember/deletePolicy/deleteFact 共享 _pendingDelete 二次确认逻辑， 而 writeMessage/queryPolicies/queryMembers/queryFacts 又各自内联 cloud.callFunction + .catch(e => console.error(...)) 重复模式。

_TOOL_DEFINITIONS（L235-468，230 行内联 JSON Schema）与 _dispatch case 一一对应但无编译期校验——新增工具需同步修改两处，漏改即静默失败。

深化方向

把"对话后处理"建模为四阶段管道，每阶段独立接缝： 意图识别 → 工具执行 → 确认流转 → 持久化。 工具定义与 dispatch 由注册表驱动（声明式），消除 switch 与 schema 双写。

收益
  • Locality：理解"用户点击确认卡片后发生什么"不再跨越 5 函数 3 云函数
  • 测试性：每阶段可独立单测（意图识别纯函数、确认流转状态机）
  • Leverage：注册表使新增工具成本从"改 3 处"降到"加 1 条注册"

候选 #3 · v2-context.js 返回 { markdown, raw } — 接口泄漏使深模块变浅 Strong

涉及文件
cloudfunctions/_shared/v2-context.js · cloudfunctions/conversationAI/index.js (L116-154) · cloudfunctions/reportAI/index.js (L363-410)
问题

v2-context.js L68-70 的 JSDoc 明确暴露 dual 返回结构： 

@returns {{ markdown: string, raw: { family, members, finances, facts, cashValues } }}
         markdown: 供 AI 消费的上下文文本
         raw: 内部查询的原始数据，供调用方复用避免重复查询

但两个调用方都绕过 markdown，从 raw 重新组装自己的上下文：

  • conversationAI L124-154：拆 raw → 额外查 policies → 用 _memberTable/_financeTable/_policyTable 重新渲染表格 → 拼接到 ctx.markdown
  • reportAI L367-410：拆 raw → 自行计算 totalPremium/premiumRatio → 构建 structuredMd/summaryMd/hintsMd → 拼接到 ctx.markdown

更隐蔽的是：_memberTable/_financeTable 在 v2-context.js 内部定义，conversationAI 却通过 require('./_shared/v2-context')._memberTable 直接导入——这些"内部"渲染函数事实上是被外部调用的第二接口。

深化方向

把"哪些集合 → 哪些表格 → 哪些附加计算"作为场景化配置。调用方只声明场景（conversation / report）和额外需求（需 policies 明细 / 需保单汇总计算），由模块统一产出完整 markdown，不暴露 raw。

收益
  • Interface 收敛：从"5 集合形状 + 4 渲染函数 + 1 markdown"降到"1 个 markdown"
  • 消除候选 #2 的根因：conversationAI 的 _buildToolContext 不再需要，postProcess 自然瘦身
  • 测试性：场景配置可表驱动，新增场景零代码改动

候选 #9 · errorHandler 仅 chat-panel 使用，3 个页面 ad-hoc 处理 Worth exploring

涉及文件
miniprogram/utils/errorHandler.js · miniprogram/components/chat-panel/index.js · miniprogram/pages/{clients,index,report}/index.js
问题

errorHandler.js 提供 handle（自动 toast + 日志 + 上报）、getErrorInfo、showSuccess 等，错误码映射表覆盖 400/401/403/404/500/NETWORK/TIMEOUT。

clients/index.js L19:  '加载失败，请下拉重试'

index/index.js   L139: '写入失败，请重试'

  • Locality：错误码 → 文案映射集中一处
  • 不强制 UI：纯函数接缝，toast 时机仍由调用方控制

候选 #10 · insurance_period 解析逻辑前后端三份实现 Strong

涉及文件
cloudfunctions/_shared/policy-status.js (L18-73 parseExpiry) · miniprogram/utils/report-builder.js (L321-335 _parseExpiryYear) · cloudfunctions/reportAI/index.js (L522-535 _parseExpiryYear)
问题

三处独立实现"保障期文本 → 到期年份"解析，行为互异：

输入 policy-status.js report-builder.js (前端) reportAI/index.js
"至70周岁" 年份（用 age 推算） null（缺 age） '-'
"终身" effYear+105-age null '终身' (字符串)
返回类型 {year, date, label} number|null string

后果：同一保单在前端报告（report-builder）和后端 AI 上下文（reportAI）中可能显示不同的到期年份。 policy-status.js 是权威源（注释自称"纯函数，可单元测试"），但前端无法通过 CONTRACT_FILES 获取它（不在列表中，且依赖 age 参数）。

深化方向

两条路：
