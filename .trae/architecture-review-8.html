Problem

handlers.js 是一个浅模块——接口面几乎与实现等宽。20+ 个 action 共享同一作用域，辅助函数（_syncFactToMember、_writeMemberFact 等）散落各处，测试必须通过整个云函数入口才能触及，缺乏局部性。

Solution

按领域拆分 handlers 为 5 个写入模块：family-write（家庭生命周期）、 member-write（成员 CRUD + 冲突检测）、 fact-write（三元组写入引擎 + 策略）、 policy-write（保单入库 + 拆解）、 profile-write（画像同步）。 入口文件保留路由表，每个模块暴露窄接口。

Wins

  • • 局部性：事实写入逻辑集中在 fact-write，bug 定点修复
  • • 测试面收窄：每个模块独立单测，无需走云函数入口
  • • 接口变窄：每模块 3-5 个导出，而非 20+
  • • AI 导航友好：按领域命名，意图直接映射文件

conversationAI 与 dataWrite 共享 _shared 写入模块，直接同进程调用

Files

  • cloudfunctions/conversationAI/index.js
  • cloudfunctions/dataWrite/handlers.js
  • cloudfunctions/_shared/memberRepo.js
  • cloudfunctions/_shared/writeSeam.js

Problem

conversationAI 的 _callWrite / _callQuery 通过 cloud.callFunction 跨云函数调用 dataWrite / dataQuery， 导致：(1) 运行时紧耦合——dataWrite 接口变动会静默破坏 conversationAI； (2) 性能损耗——每次工具调用多一次云函数冷启动； (3) 测试困难——必须 mock 整个 cloud.callFunction。

Solution

在 _shared/ 中建立 writeService 与 queryService 两个服务层模块， 封装写入/查询的领域操作（addPolicy、addFact、queryPolicies 等）。 conversationAI 直接 require 这些服务模块同进程调用， 不再走 cloud.callFunction。dataWrite / dataQuery 云函数改为这些服务的 HTTP 适配层，供前端调用。

Wins

  • • 消除跨函数耦合：编译时依赖替代运行时依赖
  • • 性能：工具调用免去额外云函数冷启动
  • • 可测试性：服务层可直接单测，无需 mock cloud SDK
  • • 单一真相：dataWrite 与 conversationAI 走同一条写入路径

Files

  • cloudfunctions/dataWrite/handlers.js (addFact)

Problem

addFact 函数同时承担：策略查表、dedup 实现、versioned 实现、成员反向同步、 subject 解析、object 解析等 6 项职责。FACT_STRATEGIES 是 20+ 项的 字符串映射表，与执行逻辑在同一文件，新增谓词策略需要同时改配置和实现分支， 且无法独立测试策略行为。

Solution

抽离 factEngine 模块：策略注册表（dedup / versioned / append-only 等）、谓词 schema 定义、写入钩子（memberSync、 policySync）。addFact 变成薄路由，调用 factEngine.write(fact)。 新增策略只需注册新策略类，不动主流程。

Wins

  • • 策略可测试：每个策略独立单测
  • • 开放封闭：新增谓词不改主函数
  • • 钩子可组合：memberSync 等后置动作可插拔
  • • schema 集中：谓词定义与策略在一处

Problem

_shared/ 目录有 27+ 个文件，其中多个是不足 50 行的浅工具模块 （calc-age ~40 行、completeness ~15 行、report-fields ~30 行、 parse-expiry ~50 行等）。每个模块只有 1-3 个导出， 接口几乎等于实现——删除模块后，复杂度只是移到调用方，不会消失。 调用方需要 import 多个小模块，认知跳数高。

Solution

按领域聚类合并浅模块到 domain/ 子目录： member-tools（年龄计算 + 维度 + 匹配）、 policy-tools（状态 + 到期 + 表格 + 现价匹配）、 report-tools（字段契约 + 完整度 + 阈值）。 每个模块内部仍保持函数独立，只是共享同一文件。

Wins

  • • 减少认知碎片：27 → ~18 个模块，按领域导航
  • • 减少 import：调用方一次引入领域工具集
  • • 保留局部性：函数仍独立，只是文件聚合
  • • 同步脚本更轻：更少文件需要复制分发

  • cloudfunctions/dataWrite/handlers.js
  • cloudfunctions/dataQuery/handlers.js
  • scripts/sync-shared.js (CONTRACT_FILES)

Problem

错误码契约分散在两处：云函数层返回 {code, msg} （各 handler 内联定义），前端 errorHandler.js 维护 ERROR_MAP 映射。两者可能漂移——后端新增错误码前端不知道， 文案不一致。目前只有 400/401/403/404/500 五个通用码， 但随着业务增长，业务错误码（409 冲突、needsConfirm 等）会增加。

Solution

建立 error-codes.js 共享模块（类似 thresholds.js 的跨树契约模式），定义错误码枚举 + 用户提示文案 + 严重级别。 云函数层抛出 AppError(code, details)，前端 errorHandler 消费同一映射表。 通过 sync-shared.js 的 CONTRACT_FILES 机制同步两端。

Wins

  • • 单一真相：错误码与文案只定义一次
  • • 防止漂移：两端自动同步，不会出现"后端有码前端无提示"
  • • 可扩展：业务错误码增长时仍保持一致
  • • 测试友好：错误码可枚举，便于断言
