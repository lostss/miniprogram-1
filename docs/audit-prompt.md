# 专项审计提示词（audit-prompt）

> 用途：向子代理下达只读审计任务时的标准提示词。目标是在**成本 / 质量 / 边界**三者间取得可复现的平衡。
> 来源：2026-09-12 四份并行审计的复盘（UX 代理 2/3 条 P0 根因判定错误，需父代理复核推翻；两份代理范围重叠导致重复付费）。
> 用法：复制 §1 模板 → 填写 §2 的变量 → 附上 §3 的固定项目事实 → 完成。

---

## 0. 为什么需要这份规范（复盘结论）

| 症状 | 根因 | 规范中的对策 |
|---|---|---|
| 子代理把「已记录的取舍」当新缺陷报 | 提示词未内置项目已决策事项 | §3 已记录取舍白名单（明确"不要报"） |
| P0 断言根因判错（单点 file:line 就下结论） | 只要求 file:line，未要求因果链 | §1 强制「≥2 处独立位置串成写入→存储→读取→消费」 |
| 两个代理读同一批文件 | 未划定互斥范围 | §1 范围写死"不读"清单 + §4 分工矩阵 |
| 每次审计全量重读源码 | 提示词无状态 | §1 必填「上一轮 findings」，只报差异 |
| 「风格偏好」混进缺陷列表 | 无判定标准 | §1 强制类型三分类，偏好默认不改 |
| 输入成本 ≈ 3万 token/代理 | 未给项目事实，需自行重新发现 | §3 直接投喂，省去发现成本 |

**成本参考量级**（2026-09-12 实测）：`cloudfunctions` 5,916 行 / `miniprogram` 8,822 行；单个全量审计代理输入约 2.6–3.6 万 token。按本规范裁剪范围 + 投喂事实后，预计输入 -30~40%、输出 -20%、父代理复核调用 -50%。

---

## 1. 提示词模板（全文复制后填空）

```
You are a helpful assistant. 对 <PROJECT_ROOT> 做「<TOPIC>」专项审计。
只读：不修改任何文件，不创建文件（除临时脚本，用后删除并确认 git 工作区还原）。

## 项目事实（直接采信，不要重新发现）
<粘贴 §3「固定项目事实」整段>

## 上一轮已报告（只报差异，未变化项写「未变」即可）
<粘贴上一轮 findings 表；首次审计写「无，本次为基线」>

## 范围（严格，不得越界）
只读：<精确文件/目录清单>
不读：cloudfunctions/<fn>/_shared/**（自动同步副本，禁止作为证据）、node_modules、其余工具规则镜像目录
例外：tests/** 仅当怀疑某条测试断言"固化"了缺陷时才读该单个文件，并在证据中说明

## 方法（按序执行）
1. 先跑验证锚点，把原始输出摘录进报告开头：
   - `node scripts/sync-shared.js --check`
   - `npx jest --silent`
   锚点失败时**先报告失败**，不要继续审计（可能正在改代码）。
2. 对每条候选问题，必须用 **≥2 处独立位置的代码**串成完整因果链：
   写入端 → 存储形态 → 读取端 → 消费端（UI / AI 上下文 / 导出）
   只有单点证据的，降级为「线索」，不得列为缺陷。
3. 涉及单位/枚举/默认值时，必须同时给出「另一条同义路径」的对照（如另一处 sheet、
   另一个云函数、前端镜像），否则判为线索。
4. 涉及 UI 行为（picker 回落、refresher 复位等）由**框架行为**推定结论时，
   必须显式标注「推定依据」并把置信度降为「高」。

## 输出（严格按此格式，不写过程叙述、不写背景复述）
### A. 验证锚点结果
<sync-shared / jest 原始摘要>

### B. 缺陷表
| # | 现象 | 因果链（file:line → file:line → …） | 置信度 | 类型 | 建议改法 |

- 置信度：`确定`（完整链均读到）/ `高`（链中一环为框架行为推定，须附推定依据）/
  `线索`（单点证据，不列入缺陷计数）
- 类型：`真实缺陷` / `设计取舍` / `风格偏好` —— 后两类**默认不改**，仅归档
- 排序：按「改动成本 ÷ 影响面」升序（便宜且影响大者在前）
- 上限：真实缺陷 ≤ 10 条。宁缺毋滥——**一条错误断言的成本 ≥ 三条正确发现**
  （父代理需为每条错误断言付出验证与推翻成本）。

### C. 未覆盖 / 存疑
本次因范围或时间未验证的点，明确列出，不要猜测填充。

### D. 与上一轮的差异
仅列「新增 / 已修复 / 仍存在」三栏。
```

## 2. 变量填写要点

| 变量 | 要点 |
|---|---|
| `PROJECT_ROOT` | 绝对路径，避免子代理自行推断 |
| `TOPIC` | 单一主题（如"状态枚举一致性"）。**不要一题多主题**——多主题必然导致范围膨胀与浅层结论 |
| 范围清单 | 用精确路径，不要写"相关文件"。宁可拆成两次审计 |
| 上一轮 findings | 直接粘贴表格。这是增量审计能成立的前提 |

## 3. 固定项目事实（每次原样粘贴）

```
权威源与同步
- 共享模块唯一权威源：cloudfunctions/_shared/**。
  cloudfunctions/<fn>/_shared/** 是 scripts/sync-shared.js 自动下发的副本，
  禁止阅读、禁止作为证据、禁止作为修改目标（改主源才是正确改法）。
- 跨树契约（权威源同时同步到 miniprogram/utils/，共 9 个）：
  thresholds.js / amount.js / gap-core.js / pii-rules.js / parse-expiry.js /
  ocr-confidence.js / injection-guard.js / readiness.js / calc-age.js
- 验证锚点：`node scripts/sync-shared.js --check`（检测副本漂移与依赖缺声明）、
  `npx jest --silent`（当前基线 88 suites / 968 tests）。

已记录的设计取舍（属「设计取舍」类，**不要作为缺陷上报**）
- writeSeam.batchTx 不真正回滚，仅并发执行并汇总错误（有意为之，调用方需自行处理 partial）。
- reportAI 的 CAS 脏值分支忽略锁并继续生成（有日志）。
- reportAI 在成功/解析失败/异常各路径均释放 analysis_lock_at（已完备）。
- policy-read / reportPdf / cash-value-read 读取失败直接抛错不降级（"核心数据宁失败不给错内容"）。
- 报告基础版（7 章）为纯规则引擎、不消耗 AI；深度分析才走 reportAI。
- facts 采用 versioned/dedup 双策略，更新走 supersede 保留审计轨迹（零物理删除），
  唯一例外是 deleteFamily 的物理级联删除。
- 客户版（share=1）：脱敏姓名/保单号，保留 AI 深度分析叙事，隐藏编辑/对话/FAB。

已知的同名不同义陷阱（审计时须区分，勿误引）
- miniprogram/utils/errorHandler.js（前端：_classifyError/handle/getErrorInfo + toast + 上报）
  与 cloudfunctions/_shared/errorHandler.js（后端：仅 wrapError）——同名、不同 API。
- families.financial_snapshot：同一名字指两样东西——DB 内嵌字段（遗留，已停止维护）与
  loadFamilyView 派生的内存视图（万口径）。讨论它之前先确认调用方是否经过 loadFamilyView。
- miniprogram/utils/ 与 cloudfunctions/_shared/ 下的同名文件（如 amount.js）可能是
  "契约镜像"（由 sync-shared 同步，逐字节一致）而非"重复实现"——先跑 --check 再下判断。

易混淆的三类"看起来像缺陷"的正常现象
- 一段代码有注释自述历史事故（如"原实现…已修复"）→ 是已修状态，不是当前缺陷。
- 某函数零调用方但仍是云函数公开 action 且有测试覆盖 → 是契约位/降级路径，不是死代码。
  判定死代码须同时满足：无调用方 + 未登记在 miniprogram/utils/apiClient.js 的 DIRECT_FN
  或云函数 handlers 映射中 + 无测试覆盖。
- 副本文件与主源内容不同 → 先跑 --check；通过则说明你读的是过期副本。
```

## 4. 分工矩阵（避免范围重叠）

| 审计主题 | 只读范围 | 明确不读 |
|---|---|---|
| 云函数与共享层 | `cloudfunctions/_shared/**` + 各函数 `*.js`（非 `_shared`） | `miniprogram/**` |
| 前端渲染与数据流 | `miniprogram/pages/**`、`miniprogram/utils/**` | `cloudfunctions/**`（除契约比对时读 `_shared` 对应文件） |
| UX / 交互 | `miniprogram/pages/**/*.wxml,*.wxss`、`components/**/*.wxml,*.wxss` + `app.wxss` | `cloudfunctions/**`、`utils/**` |
| 数据一致性 / 契约 | `cloudfunctions/_shared/{amount,thresholds,gap-core,parse-expiry,policy-status,policy-table,completeness,report-fields}.js` + `miniprogram/utils/edit-form.js`、`report/*` | 无关业务逻辑 |

> 关键：**UX 审计不重读 JS 逻辑**，其输入应是「前端/数据一致性审计已产出的结论清单」，职责是**验证与补充交互层证据**，不重复发现。

---

## 5. 反模式（禁止）

| 反模式 | 后果 |
|---|---|
| 一个代理覆盖多主题 | 每条结论都浅，且范围膨胀到全仓库 |
| 只给 file:line 不给因果链 | 产生"带行号的错误断言"，验证成本高于重新审计 |
| 未附上一轮 findings | 每次全量重读，无法增量；用户改代码后结论随即过期 |
| 未跑验证锚点 | 可能在代码半改状态下审计，结论不可用 |
| 未限定"不读副本" | 子代理读 `_shared` 副本得出与主源相反的结论 |
| 要求"尽量全面" | 输出以量取胜，含大量偏好项，稀释真实缺陷 |

---

## 6. 父代理复核清单（收到报告后必做）

1. 每条「确定」级缺陷，**独立重读因果链两端**（写入端 + 消费端）各一次。
2. 每条「高」级，核对推定依据是否成立（框架行为是否真是那样）。
3. 「线索」级不进结论表，但可留作下一轮范围。
4. 报告一旦有 ≥1 条错误断言，把该代理的范围清单与主题收窄一半后再派。
