# 保小秘（miniprogram-1）

面向保险代理人的「客户保障报告」微信小程序。以**报告**为核心产物（活文档），对话与 OCR 为辅助录入手段。
详细产品与架构说明见 `CONTEXT.md`、`docs/prd.md`。

### 测试基础设施

- **DB mock 单一事实源**：`tests/helpers/memory-db.js`（2026-09-15 架构审查候选 4）。
  tests 下原有 31 份手写 DB mock 各自重写同一套原语，正逐步收敛到它；**新测试一律用它**，不要再内联 `mockMakeDb`。
- **该不该迁的判据**（2026-09-15 补，避免机械替换）：
  - **迁**：手写 mock 在**重新实现通用原语**（自己写 `matchWhere`/`collection()`/`doc()`/`add()`）→ 这类是纯重复，换 adapter 后
    查询条件第一次真正生效，常能暴露被掩盖的问题（已实证见下）。
  - **留**：为断言**调用形状/调用序列**而写的定向桩（例如 `report-versions` 用 `_doc/_remove/_createCollection` 断言归档+清理
    顺序、`db-helpers` 用分页脚本桩断言 `skip/limit/orderBy` 入参、`ai-gateway` 用 `quotaDb` 断言 `$inc` 入参）。
    它们不是重复实现而是**接口契约断言**，换掉只会丢覆盖；adapter 也没有 `createCollection` 这类少见 API。
  - 迁移进度：31 份 → 已收敛 **15 份**（`crud-gaps`/`dataWriteHandlers`/`deleteFamily`/`queryMemberProfile`/`queryHomeList`/
    `queryFamily`/`writeSeam`/`searchFamilies`/`policy-read`/`policy-locate`/`memberStore`/`member-conflict`/`updateFamily`/
    `phase4FactSync`/`writePoliciesBatch`）。
  能力：
  - **真实 where 过滤**（`eq/neq/in/nin/gt/gte/lt/lte/exists/all/or/and`）与 `db.RegExp({regexp, options})` 模糊匹配；
  - `add({data})` 平铺落库；`update` 支持 `$inc/$push/$pull/$set`；`doc()` 单文档语义；`count()`
  - `opts.spy`：调用记录 `{ queries, adds, updates, removes, counts }`（供"是否发生某次写入/查询"类断言）
  - `opts.failCollections`：按集合名注入查询失败（数组或**返回数组的函数**——测试会重新赋值变量时用函数形式）
  - ⚠️ adapter **不返回全表**：旧手写 mock 的 `where()` 多为空实现，迁移后查询条件才第一次真正生效
- ⚠️ 迁移时暴露的易踩点（均已实证）：
  1. **`_openid` 必须与实际生效的 openid 一致**——`createHandler` 优先取 `wxContext.OPENID`，
     `event._authOpenid` 仅在无 OPENID 时兜底。空实现 mock 让这个不一致长期隐性（症状：迁移后成片 404）。
  2. **业务保单要带 `id` 字段**：`locatePolicy` 按 `id` 定位、不是 `_id`
     （旧 mock 因为恒返回全表，靠"表里只有一条"侥幸命中——该路径实际从未被测过）。
  3. **store 引用写法**：推荐"每次 `database()` 新建 adapter"（`database: () => makeMemoryDb(mockStore)`），
     此时 `beforeEach` 重建 `mockStore` 无妨。若测试一次性构造（`const db = makeMemoryDb(store)`），
     则 `beforeEach` 必须**原地清空**（`store.families.length = 0`）而非重新赋值。
     另：**被测模块若在 `require` 阶段就取 `cloud.database()`，adapter 必须加载期构造**，
     延迟到 `beforeEach` 会拿到 `null`（症状：`Cannot read properties of null (reading 'command')`）；
     且 `jest.mock` 工厂引用的外部变量名**必须以 `mock` 开头**，否则 jest 直接拒跑套件。
  4. **`add({data})` 落库是平铺的**：旧桩常写成 `add(data)` 再 `{_id, ...data}` → 落库凭空多一层
     `data` 嵌套，于是测试断言的 `row.data.xxx` 在生产中**并不存在**（`writePoliciesBatch` 9 个用例即此）。
     迁移时必须把断言改为平铺字段。
  5. **恒返回 `{updated:1}` 会吃掉"命中 0 条"分支**：`updateFamily` 的"无匹配 → 404"从未被覆盖
     （旧用例名自述"mock 局限"）。迁移后按真实 `stats.updated` 断言。
  6. **桩替生产"放水"会掩盖越权**：`member-conflict` 旧桩在匹配前 `delete f._openid`（因为 seed 不带该字段），
     使"查询是否真的按 `_openid` 隔离"彻底无法验证。迁移时 seed 必须补齐 `_openid`。

## 事实体系（2026-09-14 重构）

**背景**：原设计用「66 谓词准入表」——`predicate` 必须从 enum 选，未命中则兜底 `备注`/`有特征`。
实测两个致命缺陷：① 非标信息（如"公司团险在职有效"）落进 `备注` 后**没有任何消费点**；
② 66 谓词中约 45 个写进 facts 后在画像里完全不出现（消费侧 `EXTRA_PREDICATES` 白名单只放行 8 个）
→ **等于没采**。

**现在的结构**（单一事实源 `cloudfunctions/_shared/fact-vocab.js`）：

| 字段 | 性质 | 作用 |
|---|---|---|
| `predicate` | **开放**（AI 原话） | 保真存储，不再受词表限制 |
| `kind` | **闭合 4 值** | 决定消费方式：`fact` / `constraint` / `relation` / `lead` |
| `axis` | **闭合属性槽**（可空） | 归一化目标：命中才参与同槽消解与确定性计算 |

**关键原则**：字典不做"准入闸门"，只做"归一化建议器"——`axis` 未命中**不丢信息**，事实仍按 `kind`
进入 AI 上下文。多跳推理要靠的是"边的端点确定"（`object_id`），而不是"谓词必须字典化"。

**消费侧**：`familyPortrait.buildPortrait` 输出 `factsByKind`（全量按 kind 分组，仅排除已进结构化字段与保障边的），
`renderPortraitMarkdown` 渲染为「分析约束 / 家庭关系 / 待核实线索 / 其他事实」四段。
AI 拿到的是**语义完整的语境**，跨表推理由 LLM 在文本里完成，无需图遍历。

**报告页「客户档案」**（`miniprogram/utils/facts-view.js`，2026-09-14）：
同一批 facts 按「信息稳定性」呈现，而不是时间流水——

| 档 | 来源 | 规则 |
|---|---|---|
| 关键属性 | `axis` 命中展示槽 | 按成员聚合、常驻顶部、**不截断** |
| 需要留意 | `kind='constraint'` | 约束/时效，直接影响判断 |
| 待核实 | `kind='lead'` | 显式标"未确认"（防被当成客户确认的事实） |
| 记录时间线 | 其余事实 | 按时间倒序，截 20 条（仅复盘用） |

**保单节点属性不进档案**：`queryFacts` 默认排除 `subject_type='policy'`——它们已由「保障汇总 + 附录保单明细」
承载，混进来会把人员信息挤出截断窗口（每张保单约 10 条，5 张保单即 50 条）。
客户版走同一函数的不同规则：不给线索、不给时间线、只保留已确认的客观信息（`confidence ≥ 0.8`）。

### AI 用量/成本口径（2026-09-12 探针查实并修复）

| 来源 | 写入口 | 可读字段 | 用途 |
|---|---|---|---|
| `operation_logs`（`logAction: 'ai_call'`） | `_shared/ai-client.js` `_observe` | 顶层 `purpose/model/status/tokens/duration_ms/_openid` | 每次 AI 调用一条，覆盖面最全 |
| `operation_logs`（`action: 'ocr_recognize'` / `'ai_extract_parallel'`） | ocrService `logOperation` | `meta.tokens`（含 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`） | OCR 提取的真实 usage |
| `agent_logs`（过滤 `cost != null`） | `_shared/ai-gateway.js` `_writeLog` | `tokens{input,output,total}` + `cost` | **唯一**拆了未命中/缓存命中/输出三段的成本口径 |
| `agents.token_used_monthly/total` | `bumpAgentTokens` | token 总数 | 用户月度配额，只加不减 |

**两个必须知道的坑**：

1. `agent_logs` 是「成本日志 + 业务事件日志」混装——同一 action 可能有两类记录：一条来自 gateway
   （带 `tokens`/`cost`），一条来自业务层（`model: ''`、`tokens: null`、`cost: null`）。
   统计务必**过滤 `cost != null`**，否则条数虚高、均值被稀释。
2. 2026-09-12 之前由 `@cloudbase/node-sdk` 写入的 `ai_call` 观测，业务字段被整体包在 `data`
   子对象下（读作 `data.purpose` / `data.tokens`），按顶层字段查会得到 0 条——数据在库但"不可见"。
   **该批历史已于 2026-09-12 迁移完毕**（142 条 `data.*` 上提为顶层、`_openid`/`created_at` 复位，
   一次性函数 `migrateObservLogs` 跑完即删）。若日后仍见 `data.*` 形态，说明又有写入路径走回了
   node-sdk 的 `add({ data })`，那是回归，不是历史遗留。

**本次修复清单**（根因 + 连带）：

- `_observe` 换回 wx-server-sdk 写入 → 字段平铺（`ai-client-observe.test.js` 有回归断言锁死）
- 失败调用也记账：`err.usage` 透传给 `_withObserve`，两个直连函数整体纳入观测——
  原先 429/non-2xx/ai_format/ai_empty **完全不入账**，而 ai_empty 在本项目是高频已知故障
- `purpose` 在关键调用点补业务语义（`conversation_phase1`、`conversation_retry_direct`、
  `ocr_extract`、`report_generate`），此前只能反映客户端函数名
- `tool-orchestration.js` phase1 直连补 `openid`——实测该路记录 openid 为空，归因与配额全漏
- `ocr-extractor.js` 的 `ctx.model` 归因修正：曾把 hy3 记成 `deepseek-flash`，成本低估约一个量级
  （注意：只影响 `agent_logs` 的 `cost`；`operation_logs` 的 `model` 来自真实请求模型，一直是准的）
- `bumpAgentTokens` 改 upsert：agents 未建档时原先命中 0 条、静默丢弃（配额虚高）
- **直连通道显式补记账**（`tool-orchestration.js` `_recordDirectUsage`）：phase1 与强指令重试走
  DeepSeek 直连，**不经 ai-gateway**（原因见下），原先既不写 `agent_logs` 也不计用户配额——
  对话是最高频调用，这是最大的漏账口。现按 gateway 同口径补记（同一 `calcTokenUsage` 定价 +
  同一 `agents` 计数），失败也留痕（带已收到的 `usage`）。
  ⚠️ **不要把这两处改成 `safeCallChatWithTools`**：gateway 的 `_secureInput` 会对每条 message
  （含塞满工具协议与客户档案的长 system prompt）做 `sanitize`，而 `sanitize` 按
  `SECURITY.MAX_INPUT` **截断**（`pii-rules.js`）→ 会截断 prompt、直接损坏工具决策。
