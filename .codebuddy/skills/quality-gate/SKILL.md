# Quality Gate（根因导向质量门禁）

## 核心原则

**治根因，不治症状。** regex 脚本只能抓已知症状，抓不了根因滋生的新错。本 skill 用 6 条根因检查提问拦截"思维过程"层面的认知失败，并随每次犯错动态收敛。

**Iron Law：**
```
交付前未逐条显式回答检查清单 = 不许 ship
修复后未提取根因更新错误库 = 修复未完成
```

**违反规则的字面即是违反规则的精神。**

---

## 一、交付前检查清单（6 条根因提问）

每次编写/修改代码准备交付前，**逐条显式产出回答**（不答不许 ship）。每条问的是"你的思考对不对"，不是"代码长什么样"。

### #1 假设验证
本次改动有哪些隐含假设？逐条列出，每条标注依据（文档/代码/契约/测试）。
- **无依据的假设不许写进代码**——先验证再写。
- 典型失败：假设"查询有默认顺序"、假设"被调函数接受任意入参"、假设"运行时保持状态"。

### #2 契约对齐
本次调用了哪些已有函数/模块？逐一回看被调方的入参约束、返回格式、错误码，确认调用方传值能通过校验。
- **写调用方前必须回看被调方契约**，默认值必须能通过校验。
- 典型失败：调用方传 fallback 默认值，但该值不符合被调方校验 → 运行时 404/400。

### #3 消费者视角
假设自己是下游消费者（AI / 前端 / 报告引擎 / 其他函数），看到本次产出能正确理解吗？有无内部 ID、内部字段、未映射外键外泄？
- **产出层（给 AI 读的文本、给前端的响应）禁止暴露内部 _id/外键**，必须映射为人类可读值。
- 典型失败：上下文文本输出 `member_id` 而非姓名；元数据硬编码不分来源。

### #4 运行时模型
本次用了状态/缓存/节流/单例/模块级变量？它依赖的运行时特性（云函数无状态 vs CloudRun 长驻 vs 浏览器）在目标运行时是否成立？
- **云函数禁止用模块级变量做跨调用状态**（节流/缓存），冷启动会重置；改用 DB 时间戳或外部存储。
- 典型失败：模块级 `let _last = 0` 做节流，云函数冷启动后失效。

### #5 边界覆盖
本次"最简版"覆盖了哪些边界？未覆盖的缺口是什么？是否可接受（显式列出，不默认"应该没事"）？
- **"能跑" ≠ "正确"**。最简版的已知缺口必须显式声明，不能藏在"应该没问题"里。
- 典型失败：用 `slice(0,N)` 当"取最近 N 条"，未验证数据有序性边界。

### #6 正确性证据
本次改动的正确性靠什么证明？单测 / 类型检查 / 走查 / 运行验证？
- **只有"看起来对"不达标**。新建被多函数调用的核心层必须有单测。
- 典型失败：无单测就交付，错误堆积到事后审计才暴露。
- 典型失败：用**间接现象**推断状态（试一次认证、扫一眼日志、凭"应该"），而非查**权威状态源**——状态类问题（是否已注册/已生效/已部署）必须找能直接回答事实的通道核对，间接推断会多绕一轮并把排查方向带偏。

### 回答格式
```
#1 假设：[列出] 依据：[标注] → 通过/待验证
#2 契约：[列出调用] 校验：[对齐结果] → 通过/待修复
#3 消费者：[视角检查] → 通过/待修复
#4 运行时：[状态使用] 成立性：[结论] → 通过/N/A
#5 边界：[覆盖] 缺口：[列出] → 可接受/待补
#6 证据：[类型] → 通过/待补
```
任一"待修复/待验证/待补"未解决前，不许声称完成。

## 二、修复后根因归因与动态更新

**每次修复 bug 后必须执行**（不止于让代码能跑）：

1. **追问根因**：不停在症状（"slice 没配 orderBy"），追问"为什么会犯这个错"——归到思维/流程层面。
2. **归类**：映射到 6 类根因之一（假设未验证 / 契约不对齐 / 视角错位 / 运行时偏差 / 边界缺失 / 无证据）。
3. **更新错误库**（见下表）：
   - 新根因类别 → 检查清单加一条 + 错误库加行
   - 已有类别 → 强化该条典型失败示例 + 错误库加行
4. **同步检查清单**：若错误库新增 ≥2 条同类别，说明该条检查力度不足，强化措辞或加红旗。

## 四、红旗——STOP

- 想说"应该没问题"/"大概能跑" → 回到 #5/#6
- 写了 fallback 默认值 → 回到 #2 确认能否过校验
- 产出文本里出现 `_id`/`member_id` 字面量 → 回到 #3
- 云函数里写了模块级 `let` 做状态 → 回到 #4
- 用 `slice`/`limit` 取"最近 N 条" → 回到 #1 确认有序性
- 写了安全守卫/权限拦截条件 → 回到 #1 代入攻击场景验证条件方向（如 prod+devMode 是否真被拦）
- 写操作用 `.catch(()=>{})` 静默 → 回到 #5 确认失败是否需上报（写 vs 读/标记要区分）
- 用间接现象推断状态（试一次 / 看一眼 / 凭"应该"）→ 回到 #6，找能直接回答事实的权威通道直查
- 即将声称"完成"但没产出检查清单回答 → 违反 Iron Law

## 五、合理化防御

| 借口 | 现实 |
|------|------|
| "改动很小不用走清单" | 小改动照样犯根因错（缺陷3就是一行 fallback）|
| "时间紧先 ship 后补" | 事后补的成本 ≥ 走清单的 3 倍 |
| "这个假设显然成立" | "显然"=未验证，验证前不许写 |
| "被调函数我应该记得契约" | 记忆 ≠ 契约，必须回看代码 |
| "消费者应该能推断" | 推断 ≠ 正确理解，必须显式可读 |
| "只此一次" | 没有例外 |
